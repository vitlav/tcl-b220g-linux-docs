# USB ACPI: ресурсы Linux, питание и пробуждение

В ACPI-конфигурации с управляемыми ресурсами подтверждены запуск DWC3/xHCI,
подключение обоих PHY, обнаружение USB-устройств и чтение дескрипторов.
Проверено 27 сентября 2026 года на `7.2.4-tcl-acpi-usbpm1+`.
**Системный сон, runtime suspend и пробуждение USB ещё не подтверждены.**
Изменения управления ресурсами пока не включены в опубликованную серию
патчей; эта страница описывает проверенный результат экспериментальной сборки.

## Подтверждённая работа

| Проверка | Результат | Граница утверждения |
|---|---|---|
| DWC3 и xHCI | Оба драйвера привязаны; USB2 и USB3 root hubs зарегистрированы | Регистрация USB3 root hub не доказывает передачу SuperSpeed |
| USB2 PHY | `qcom-qusb2-phy` привязан, runtime active | Полный цикл отключения/включения питания не проверен |
| USB3/DP combo PHY | `qcom-qmp-combo-phy` привязан, runtime active | Платформенный режим USB3_ONLY, ориентация NORMAL; DP и переворот Type-C не проверены |
| USB GDSC | `QCOM0897:00` — active-потребитель `usb30_prim_gdsc` | Временные удержания USB/CX сняты, оба вспомогательных устройства suspended |
| USB2-концентратор | Genesys `05e3:0608`, четыре порта, 480 Mbit/s | Чтение дескрипторов выполнено; счётчик IRQ xHCI увеличился |
| Встроенная камера | IMC `13d3:784b`, UVC на порту концентратора 4 | Подключение `uvcvideo` подтверждено; видеопоток в этой проверке не запускался |
| Остальная система | Сеть/SSH, дисплей и службы графики/звука запущены | Это не проверка восстановления после сна |

## IRQ: индекс ACPI, GSI и PDC pin

| Назначение | Индекс IRQ в URS0.USB0 `_CRS` | GSI / GIC INTID | Источник Linux |
|---|---:|---:|---|
| xHCI | 0 | 165 | GIC SPI133, level-high |
| Power event | 1 | 162 | GIC SPI130; не подменяет HS PHY |
| HS PHY | отсутствует | 163 по DT | GIC SPI131; ACPI IRQ не предоставлен |
| SuperSpeed wake | 2 | 518 | PDC6, level-high |
| DM wake | 3 | 520 | PDC8, edge |
| DP wake | 4 | 521 | PDC9, edge |

SC7180 PDC range `0 480 94` задаёт родительские **SPI**:
для pin6 GIC INTID равен `480 + 6 + 32 = 518`.
В работающей управляемой конфигурации зарегистрированы три линии PDC:
DP9, DM8, SS6. Их наличие не доказывает пробуждение: события wake ещё
не испытывались. Обработчики оставлены выключенными до подготовки сна.

Linux должен создать иерархические IRQ через PDC, а не сначала занять
те же GSI прямыми GIC mappings. Поэтому ранняя блокировка wrapper предшествует
созданию ресурсов. Для DWC3 отдельно извлекается только xHCI IRQ из USB0;
автоматическое создание платформенного USB0 с отображением всех `_CRS` IRQ
в этом режиме не используется. PDC регистрируется самостоятельным устройством,
чтобы связь USB → PDC не образовывала цикл зависимостей parent/child.

## Ресурсы управляемого host

| Блок | Адрес / ресурс | ACPI-адаптация |
|---|---|---|
| DWC3 / xHCI | `0xa600000/0xe000`, GSI165, SMMU SID`0x540` | Сохранены исходный ACPI device и IORT identity |
| QSCRATCH | `0xa6f8800/0x400` | Ресурс wrapper |
| GCC | `0x100000` | Явно включаемая USB-подсистема, ограниченные разрешённые регистры |
| Wrapper clocks | cfg_noc, core, iface, sleep, mock_utmi | Именованные CCF clocks; частоты не задаются по неподтверждённому предположению |
| Reset / power | DWC3 reset, USB30_PRIM_GDSC → CX | Именованное описание reset и реальные genpd-потребители |
| DDR interconnect | `qhm_usb3@tcl-sc7180-anoc2` → `ebi@tcl-sc7180-mc` | Обычные ICC paths и bandwidth votes |
| Register interconnect | `acm_apps0@tcl-sc7180-gnoc` → `qhs_usb3@tcl-sc7180-cnoc` | Отдельный ICC path |
| USB2 PHY | `0x88e3000/0x400` | SC7180 QUSB2 v2, GCC cfg_ahb, RPMh bi_tcxo, reset |
| USB3 PHY | `0x88e8000/0x3000` | SC7180 QMP combo, пять именованных clocks, reset phy |
| QFPROM | corrected window `0x784000/0x7a0` | Read-only NVMEM cell hstx-trim-primary, byte`0x25b`, bits1–3 |
| PDC | `0xb220000/0x30000` | Только USB pins6/8/9; прочие линии не переинициализируются |

| Питание PHY | Потребитель | Ограничение напряжения |
|---|---|---:|
| L4a | QUSB2 vdd, QMP vdda-pll, также дисплей | 880000 µV |
| L11a | QUSB2 vdda-pll | 1800000 µV |
| L17a | QUSB2 vdda-phy-dpdm | 3088000 µV |
| L3c | QMP vdda-phy, также дисплей | 1200000 µV |

Это ограничения драйверов/описания платы, не измерение напряжений.
Общие L4a/L3c используют существующих regulator providers; дублировать их
нельзя. Для обязательных ресурсов отсутствие regulator завершается ошибкой,
а не заменой фиктивным питанием. Сопоставление с DT — в [USB DT](usb-input.md#phy-и-питание).

## Свойства IORT и порядок подключения

IORT уже создаёт secondary software node с `pasid-num-bits` и, если требуется,
`dma-can-stall`. Добавление свойств clocks/reset/PHY/ICC/PDC должно сохранять
эти данные и первичный ACPI fwnode. Требуется объединение свойств с проверкой
дубликатов и корректным владением ссылками. Замена узла без сохранения свойств
или цепочка из нескольких secondary nodes не являются корректным решением.

В проверенной реализации ранний wrapper gate включается до захвата USB IRQ.
Затем регистрируются поставщики ресурсов, PHY и lookup для настоящего ACPI
потребителя, подключается USB GDSC, запускаются DWC3 и xHCI. Временные удержания
USB/CX снимаются только после проверки привязки обоих драйверов и активного
реального потребителя питания. При ошибке подготовки удержания сохраняются.

## Что ещё требуется для сна

В ACPI-ветках system/runtime suspend wrapper пока сохраняет `-EBUSY`.
Успешный запуск управляемого USB не означает поддержку сна.

1. Проверить баланс PHY/clocks/ICC/genpd при suspend/resume и отказах.
2. Квалифицировать выбор полярности DP/DM и вооружение wake IRQ через PDC;
   ошибки `irq_set_irq_type()` и `enable_irq_wake()` должны отменять переход.
3. Проверить реальный s2idle и возврат USB, ввода, сети, изображения и звука.
   Восстановление DPU после отменённого сна также требует отдельной проверки.
4. Проверить SuperSpeed с реальным устройством и обе ориентации Type-C.

Только после этих проверок можно расширять заявленную поддержку питания.

## Частоты работающего firmware handoff

На работающем public70 прочитаны только перечисленные регистры через уже
существующий GCC regmap. Записей в регистры не было; диагностический модуль
после чтения выгружен. База GCC — `0x100000`.

| Регистр / источник | Readback | Вывод |
|---|---|---|
| GPLL0 USER_CTL, offset0x0c | 0x103 | even-divider encoding1, делитель2 |
| GPLL0 через CCF | 600000000 Hz | even-выход300MHz |
| USB MASTER CFG, offset0xf020 | 0x105 | source1=GPLL0, HID5: 600MHz × 2/6 = **200MHz** |
| USB MASTER M/N/D, offsets0xf024/28/2c | 0/0/0 | M/N mode в CFG выключен |
| USB MOCK UTMI CFG, offset0xf038 | 0x1 | source0=XO, HID1: **19,2MHz** |
| USB PHY AUX CFG, offset0xf064 | 0x1 | source0=XO, HID1: **19,2MHz** |
| USB GDSCR, offset0xf004 | 0xf8222000 | PWR_ON=1, SW_COLLAPSE=0 |

Частоты декодированы по регистрам и CCF, не измерены осциллографом.
DT `assigned-clock-rates=150000000` — запрос, а не доказательство работы
на150MHz. Таблица частот текущего GCC предлагает66,666667/133,333333/200/240MHz;
перенос управления не должен без необходимости менять подтверждённые200MHz.

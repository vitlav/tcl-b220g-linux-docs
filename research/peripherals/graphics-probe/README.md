# Подготовка проверки графики TCL B220G

Статус 2026-09-08: подготовлены сбор исходного состояния и порядок испытаний. Загрузочного DRM-теста ещё нет: отсутствует проверенная реализация связки DSI → LT8911EXB → eDP. Не считать этот каталог готовым драйвером или загрузочным образом.

`collect.sh` читает sysfs, dmesg, modinfo и состояние сети/дисков. Он не загружает модули, не сканирует I2C, не переключает GPIO, не перезагружает систему. Запуск через SSH с перенаправлением stdout сохраняет лог на управляющем сервере. Проверены синтаксис и реальное выполнение; результат `baseline.txt`.

## Исходное состояние

- Ядро6.18.34-stb-qc7+, Ubuntu, EFI VGA1920x1080x32/stride7680.
- Модуль msm есть; panel_edp и ti_sn65dsi86 встроены. modinfo lontium_lt8911exb возвращает not found. TI-драйвер не подходит для обнаруженного LT8911EXB.
- MDSS, display clock controller и GPU в DT отключены; DRM card отсутствует.
- SSH через встроенный Wi-Fi работает. Все6внутренних UFS устройств RO.
- Полная копия UFS проверена; это не замена рабочей USB-загрузке при неудачном тесте экрана.

## Последовательность тестов

1. **Контроллер I2C.** В отдельном DTB, производном от реально загруженного рабочего DTB, включить только подтверждённый по ACPI контроллер a90000 и необходимые pinctrl/clock. MDSS/GPU оставить отключёнными. Сначала проверить pinmux по таблицам и текущему DTS; номер адаптера Linux не предполагать равным IC11/i2c10. Проверить появление адаптера и отсутствие регрессий SSH/клавиатуры/UFS. Не использовать i2cdetect: произвольные транзакции не нужны.
2. **Идентификация мостика.** Только после проверки шины подготовить адресный инструмент для0x29: сохранение/восстановление банка, чтение ID по установленной OEM-последовательности. FF=81/08=7F являются записями; эффект на уже работающую картинку ещё не проверен. GPIO reset не выполнять на этой стадии. Реализация инструмента пока не подготовлена, поскольку восстановление исходного состояния требует дополнительного анализа.
3. **DRM bridge.** Требуется реализация с корректными probe/attach, порядком power/reset, EDID/AUX, link training, atomic enable/disable. Внешний reference-lt8911exb.c — источник сведений о регистрах, не готовый DRM bridge. Подготовить изменения для разработчика; пакетную сборку направлять сборщику пакетов согласно правилам проекта.
4. **DSI/KMS.** Только с готовым bridge включить MDSS/DSI/PHY/необходимые clocks и связать graph endpoints. Кандидат:4lanes, RGB888, video non-burst event, тайминги настоящего EDID1920x1080. Не переносить Qualcomm enum1/36 как Linux flags, не подставлять fallback1366x768. GPU3D не является целью первого KMS-теста; его зависимости проверять отдельно.

## Журнал и возврат к рабочей загрузке

Перед изменением USB сохранить точные EFI/GRUB/DTB/initramfs и SHA256. Рабочую запись Ubuntu сохранить отдельным неизменённым пунктом. У нового теста должны быть собственные имена DTB/initramfs и ID. Пользователь предпочитает новый готовый тест по умолчанию; назначать его default только после проверки всех файлов и синтаксиса, не на стадии этого плана.

Сначала обеспечить автоподключение Wi-Fi и SSH в тесте. Писать dmesg на сервер через SSH во время probe; локальный лог в /var/log/tcl-graphics дублировать на USB только после завершения и sync. Путь rootfs — запущенный loop-образ на USB: не заменять его при подготовке.

Автоматическую перезагрузку после окончания будущего теста реализовать таймером после сохранения логов, с явной отменой. Таймер userspace не помогает при зависании ядра: тогда нужен ручной возврат к рабочему пункту. На этапе подготовки таймеры и перезагрузки не назначены.

Успех первого KMS-теста: DRM connector connected, EDID совпадает с сохранённой панелью, режим1920x1080, изображение без сдвигов/зависаний, SSH и клавиатура доступны. Чёрный экран при живом SSH отличать от зависания системы; собрать dmesg и состояние DRM перед откатом.

Основания и ограничения: ../graphics-research/README.md. Прежде чем составлять DTB первого теста, нужно проверить pinmux контроллера a90000 в реально загруженном дереве.

## Первый DTB-кандидат подготовлен

ACPI DSDT IC11: MMIO0xA90000, length0x4000, interrupt0x185. Linux GIC_SPI357 +32 =389/0x185. PEP0 IC11 содержит gcc_qupv3_wrap1_s4_clk и TLMMGPIO0x56/0x57, то есть86/87. SC7180 pinctrl qup_i2c10_default задаёт gpio86/87, function qup14. Точный смысл остальных полей Windows TLMM package не переносили наугад. В live pinmux оба GPIO UNCLAIMED; это отсутствие Linux-владельца, не гарантия состояния электрических сигналов.

На USB SHA256 рабочего sc7180-tcl-cpufreq.dtb совпал с локальным: f88a6854d0e1085b32b5f92cbca01e391b61248d512bcf00003ee080a83f7713. i2c_qcom_geni builtin, devices_deferred пуст. В live DT нужные interconnect-провайдеры и SMMU не отключены. Не использовать live FDT непосредственно как базу загрузки: он содержит адреса UEFI memory map текущего запуска.

`build-i2c-dtb.py` создаёт `sc7180-tcl-i2c10.dtb`, SHA2561929faac529880bcf7bd87d83ce30cccf0bf28c074141b61657af81fb44cc71c. Diff проверен: ровно три изменения свойств — status=okay QUP1, status=okay i2c10, clock-frequency100000 (из ACPI устройства EDP1). GPIO86/87 pinctrl остаётся исходным. Другие дочерние контроллеры QUP1 отключены; узел bridge не добавлен, I2C-транзакций к0x29 не запланировано. Probe контроллера всё же меняет clock/pinmux и ещё не испытан на железе.

`grub-i2c10.cfg` — подготовленный фрагмент, использует текущие Image и Ubuntu initramfs. DTB должен лежать на USB по `/tcl-graphics-probe/sc7180-tcl-i2c10.dtb`. Фрагмент пока НЕ установлен в действующий GRUB; текущий default не изменён. Автоперезагрузка для этого первого контроллерного теста не подключена: сначала потребуется подтвердить SSH после загрузки и собрать collect.sh.

При первой загрузке проверить адаптер по его OF-пути, не только номеру, драйвер GENI, отсутствие deferred probe/ошибок, работу Wi-Fi/SSH/клавиатуры и сохранение EFI framebuffer. После этого можно готовить адресную проверку ID; один контроллерный DTB не проверяет сам LT8911EXB.

## Адресная идентификация LT8911EXB выполнена

На той же загрузке192b0902-e812-4c64-9c93-ef4b64ebb903 выполнены транзакции через /dev/i2c-10 к7bit0x29. Первое чтение FF дважды вернуло0x12: нельзя трактовать его как достоверный номер текущего банка. Первоначальная идея сохранить/восстановить bank по чтениюFF отвергнута до каких-либо записей.

Затем выполнена ровно одна запись данных: FF=81, как в DisplayDxe0x2E640 и reference-lt8911exb.c. Чтение81:08 вернуло7F, поэтому запись access-enable не требовалась. Регистры81:00/01/02 вернули **17 05 E0**. Эти байты совпадают с примером chipid в внешнем драйвере (его printf не дополняет каждый байт нулём, поэтому строка `0xe0517` не является корректным трёхбайтным hex-представлением; при порядке high/mid/low получается E0 05 17).

Банк оставлен81, восстановление исходного неизвестного банка не заявляем. GPIO/reset, power, PLL, AUX и video timing не изменяли. Запрос чтения включает запись адреса регистра и repeated START, но не изменение его значения. Настоящая картинка визуально не проверена; EFI framebuffer зарегистрирован, SSH доступен, новых сообщений ядра после операций в хвосте dmesg нет.

Скрипт read-bridge-id.py закреплён за boot_id и OF-путём адаптера, проверяет отсутствие владельца kernel driver, не сканирует шину. По умолчанию только читаетFF. Режим --select-id-bank выполняет указанную запись и чтения; повторно запускать без необходимости не требуется. Файлы: bridge-bank-before.jsonl, bridge-id.jsonl, after-id-health.txt.

Следующее исследование: адресное чтение известного набора timing/status-регистров и сравнение с EDID, без reset/AUX/link-training. Перед ним составить whitelist регистров по OEM/reference-коду и явно учитывать смену банка. Полный dump всех регистров не нужен.

## Link training status и выходной профиль (2026-09-08)

В DisplayDxe найден статусный путь: AC:82 bit5 означает завершение, low5bits==1E выбирает строку Link train success (0x2F590–2F5EC). AC:83 и84 выводятся как panel link rate / panel link count. Сырые строки прошивки находятся по0x4769F/0x476F3/0x47709. Это позволяет читать результат без повторного training/AUX.

| Регистр | Live hex | Значение |
|---|---|---|
| AC:01 |0A|Записанный OEM параметр training|
| AC:82 |3E|По условию OEM: завершено успешно|
| AC:83 |0A|Panel link rate status|
| AC:84 |82|Panel lane count/status|
| 82:22–25 |82 00 80 00|Первый выходной профиль|
| 82:26–29 |82 00 80 00|Второй выходной профиль, тот же|

Кодировки DisplayPort в официальном Linux v6.18 drm_dp.h: DP_LINK_BW_2_7=0A, DP_LANE_COUNT_MASK=0F, enhanced frame enable=80. Источник: https://github.com/torvalds/linux/blob/v6.18/include/drm/display/drm_dp.h . Таким образом прочитанный status согласуется с **2.7Gbps/lane,2lanes,enhanced framing**. Это интерпретация LT8911EXB status по названиям OEM и стандартным DP-кодам; DPCD напрямую не читали и физическую частоту не измеряли. Текущее отсутствие ошибок канала также не измерено: training status отражает результат инициализации.

UEFI использует таблицы0x5227E=[82,81,80,80,80,80] и0x52284=[00,00,E0,C0,A0,80], общий индекс из0x7A0C1. На каждую линию пишет tableA[index],tableB[index],80,00 в82:22–25/26–29. Live соответствует индексу0, но сам firmware memory index не читали. Не назначать этим байтам значения напряжения/pre-emphasis без точного определения битов.

Скрипт read-bridge-training-status.py; данные bridge-training-status.jsonl. ТолькоFFbank writes, final81/ID17 05 E0, reset/retrain/AUX не выполнялись. Disassembly ../graphics-research/uefi-training-status.asm.

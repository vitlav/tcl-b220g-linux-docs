Дерево скопировано с предыдущей сборки, это не сборка с нуля без прежних объектов. Отдельный release; 949 модулей вместе с handoff. Конфигурация, команды и проверки в этом каталоге.

## ICE

`qcom-ice 1d90000.crypto: Found QC Inline Crypto Engine (ICE) v3.1.75`.
`A supported HWKM is not present. Supporting raw keys only.`

На всех шести UFS LUN: `num_keyslots=32`, `max_dun_bits=64`, `raw_keys=supported`, `modes/AES-256-XTS=0x1fe00`. Драйвер qcom-ice привязан; devices_deferred пуст. Все внутренние LUN и разделы остаются RO=1. Это подтверждение инициализации и возможностей, не проверка зашифрованного I/O. Запись на внутренние разделы, программирование тестовых ключей и форматирование не выполнялись. DM_CRYPT сам по себе этот ICE не использует; FS_ENCRYPTION пока выключен.

## Контроль чтения: ограниченный результат

Первые 1 MiB пяти LUN совпали с хешами непосредственно перед перезагрузкой. LUN4: до `5d96409e8786f752101fac135a1f4e79a56591487b3786852103fa2d02e5dbbf`, после `75652c87f4fed20d6378ee959f91d8bb64005378d70ad9db41dc297d10cad492`. Повторное чтение и отдельное чтение `iflag=direct` дают тот же новый хеш.

Сравнили 1 MiB с более ранним Borg-архивом `windows-20260908-lun4` (его хеш `deb847ca86be06b381fb1d8506bc730ab7073bb767c430a4d3a4ca77a7c996b4`). Отличаются только четыре байта по смещениям 0x80008, 0x80009, 0x8000e, 0x80010, все внутри раздела `limits` (начало 0x80000, длина4096). Остальная область совпадает; историческая копия GPT131072байт также совпадает. Детали `lun4-comparison.json`.

Это НЕ побайтовое сравнение непосредственно до/после ICE1: перед перезагрузкой сохранены лишь хеши. Причина и момент изменения не установлены; нельзя приписывать их ICE или считать доказанными записи прошивки. Полная целостность LUN этим тестом не проверена.

Для чтения начала Borg-поток намеренно ограничен head до1048576байт; BrokenPipe у Borg ожидаем из-за закрытия потребителем. Размер результата проверен. Архив не восстанавливался на устройство.

Логи всех шести снимков и исходные хеши сохранены в `hardware/`. Сырые байты внутренних разделов не включены в публичные материалы. Следующая проверка, если потребуется локализация изменения при загрузке: сохранить побайтовую копию начала LUN4 до и после очередной необходимой перезагрузки, без отдельного перезапуска сейчас.

## Продолжение: стабильность и назначение ICE

При uptime около3ч50мин тот же boot ID, Weston active, все внутренние LUN RO=1, deferred пуст; в журнале не обнаружено новых ошибок I/O UFS/ICE. Есть отдельная ошибка unsupported DISCARD на loop0 при143.85s — это корневой USB-backed образ, а не UFS ICE. Конфигурацию монтирования пока не меняли.

Повторное `dd iflag=direct` завершилось EINVAL. На TCL `/usr/bin/dd` — uutils coreutils0.8.0, логический сектор UFS4096байт. Причина EINVAL у dd не доказана. Контроль через Python `mmap` (выровненный буфер) + `os.open(O_RDONLY|O_DIRECT)` + `os.readv` успешно прочитал ровно1048576байт. Хеш `75652c87f4fed20d6378ee959f91d8bb64005378d70ad9db41dc297d10cad492` совпал с ранним чтением текущей загрузки. Новых ошибок в dmesg перед контрольным чтением не было. Сохранён побайтовый baseline для следующей необходимой загрузки; текущую систему не перезагружали.

Поиск строк limits в локальных xbl.bin/plat.bin и три запроса GitHub code через gh не установили писателя раздела. Это не доказательство отсутствия обращения в сжатом/ином коде прошивки. Причина исторического изменения limits остаётся открытой.

ICE — аппаратная обработка запросов накопителя через blk-crypto, не универсальное шифрование буферов. Crypto API обслуживает отдельный путь, в нашем dm-crypt используются crypto_alloc_skcipher, не blk-crypto. Для TLS/VPN этот ICE штатно не применяется.

Стандартный пользователь inline encryption — fscrypt на ext4/F2FS с inlinecrypt. Требуются CONFIG_FS_ENCRYPTION и CONFIG_FS_ENCRYPTION_INLINE_CRYPT; в ICE1 оба отсутствуют из-за FS_ENCRYPTION=n, EXT4_FS=n, F2FS_FS=m. Fscrypt шифрует содержимое/имена, но не все метаданные; корневой каталог ext4 зашифровать нельзя. Поэтому это не готовая замена LUKS для целиком зашифрованного корня Ubuntu. Текущий Btrfs root-on-USB не использует UFS ICE.

Android применяет также dm-default-key для шифрования метаданных через blk-crypto. В нашем дереве6.18.34 такого target нет; это не предлагается как готовая конфигурация текущей Ubuntu. Инициализация ICE подтверждена, реальное зашифрованное I/O и восстановление ключей после сброса/сна ещё не проверены.

Источники: https://docs.kernel.org/block/inline-encryption.html ; https://docs.kernel.org/filesystems/fscrypt.html ; https://source.android.com/docs/security/features/encryption/metadata . Версионные детали сверены также с локальными исходниками6.18.34 (Documentation/filesystems/fscrypt.rst, drivers/md/dm-crypt.c и .config).

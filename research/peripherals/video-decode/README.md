# TCL B220G: аппаратное декодирование видео

Дата:2026-09-09. Проверено на ядре6.18.34-tcl-ice1, boot7b25ec7a-df79-4fb3-aaa5-67ca093e4372.

## Исходное состояние до Venus1

Аппаратное декодирование на текущей загрузке НЕ работает/не предоставлено приложениям: Venus и VIDEOCC отключены в DT, устройства декодера V4L2 отсутствуют. Работающие Adreno618/OpenGL/Vulkan и DPU относятся к другим блокам. Камера UVC также не подтверждает Venus.

| Уровень | Установлено | Что ещё требуется |
|---|---|---|
| Драйвер SoC | В исходниках есть qcom,sc7180-venus, HFI4XX, VPU AR50; CONFIG_VIDEO_QCOM_VENUS=m | Аппаратный probe на TCL |
| DT | video-codec@aa00000 и clock-controller@ab00000 disabled | Аудит и включение зависимостей в отдельном тестовом DT |
| Firmware | Драйвер по умолчанию запрашивает qcom/venus-5.4/venus.mbn; каталога сейчас нет | Получить подходящую firmware из проверенного источника, проверить PAS/SCM загрузку |
| Интерфейс | Stateful V4L2 mem2mem | После probe проверить capabilities и форматы |
| Userspace | Через epm установлен FFmpeg8.0.1; есть h264/hevc/vp8/vp9_v4l2m2m wrappers | Wrapper в списке не доказывает наличия устройства или успешного decode |
| Реальный тест | Ещё не выполнен | H.2641080p30 → проверка кадров и CPU; далее другие режимы |

## Кодеки и ограничения

Общий код драйвера Venus содержит H.264, HEVC, VP8, VP9, MPEG2/4 и другие форматы. Поддержка конкретного SoC определяется таблицами/ответами HFI; этот перечень НЕ является подтверждённой матрицей TCL. До получения runtime capabilities не обещать4K,10bit,профили,максимальные FPS. AV1 в таблице vdec Venus отсутствует; наличие libdav1d/av1 в FFmpeg означает программный декодер, не аппаратную поддержку TCL. Аналогично CUVID wrappers не означают наличие NVIDIA.

## Зависимости для следующего аппаратного шага

Узел venus требует VIDEOCC clocks/GDSC, RPMh CX, OPP, apps_smmu stream0xc00/mask0x60, reserved-memory venus_mem, interconnect mmss_noc/gem_noc/config_noc. Исходник sc7180.dtsi: reg0xaa00000/0xff000, IRQ174. До включения проверить совпадение reserved-memory с нашим проверенным DT/UEFI и все поставщики ресурсов. Не копировать неподходящие carveout/адреса с другого ноутбука. Простого modprobe при disabled DT недостаточно. Текущую рабочую систему ради отчёта не перезагружали.

Порядок: подготовить отдельный DT+firmware; статический аудит зависимостей; сохранить рабочий пункт; при следующей необходимой загрузке проверить PAS/probe/dmesg; перечислить форматы; прогнать известный синтетический ролик с явно выбранным v4l2m2m декодером и без software fallback. Сравнить кадры/ошибки, CPU, FPS и питание с программным декодированием. Отдельно проверить Wayland display/DMABUF, затем интеграцию плеера/браузера. VA-API и Vulkan Video нельзя считать работающими по наличию Mesa/Vulkan.

## Камера — отдельная проверка

UVC USB13d3:784b, /dev/video0 capture, /dev/video1 сопутствующий узел, /dev/media0. Камера предлагает MJPEG1280x720@30, YUYV1280x720@5, низкие разрешения@30. Показ MJPEG720p30 запущен в Weston через ffplay; пользователь подтвердил живое изображение. Декодирование MJPEG/конверсия цвета в этом тесте программные; ffplay предупреждает про отсутствие ускоренной конверсии yuv422p→rgba и APP fields. Это не тест Venus.

## Сравнение CPU при полном экранном воспроизведении, 2026-09-09

Пользователь подтвердил: Big Buck Bunny через Venus «выглядит прекрасно».

Сравнение ffplay: один файл официального Big Buck Bunny H.264 Main 1920x1080 24 fps; полный экран Weston GL, звук выключен. Каждый запуск с `-ss 60`, первые 5 s исключены, далее 25 s измерения. Порядок hardware → software → hardware. Программный декодер `-vcodec h264`, аппаратный `-vcodec h264_v4l2m2m`. Остальные параметры одинаковы; число потоков — автоматическое по умолчанию. Частоты/governor не фиксировались: это нагрузка в текущем обычном режиме системы, не сравнение при фиксированных частотах или измерение энергии.

CPU процесса получен из прироста utime+stime /proc/PID/stat: 100% означает одно полностью занятое ядро. Weston — сумма процессов с comm=weston. Общая загрузка из /proc/stat нормирована на все 8 CPU; idle и iowait исключены из busy.

| Режим | ffplay, % одного ядра | Weston, % одного ядра | Общая busy, % всех CPU |
|---|---:|---:|---:|
| hardware1 | 157.2 | 6.2 | 21.5 |
| software | 78.7 | 7.4 | 12.1 |
| hardware2 | 154.0 | 6.1 | 21.1 |

Вывод: в текущем ffplay аппаратный путь требует примерно вдвое больше процессорного времени плеера (154–157% против 78.7%). Общая загрузка всей машины 21.1–21.5% против 12.1%. Нельзя утверждать, что аппаратное воспроизведение уже экономит CPU/энергию. Ранее дешёвое декодирование ffmpeg → null относится к другому пути без экранного вывода и другому ролику.

Журналы обоих аппаратных запусков подтверждают qcom-venus /dev/video2. Corrupt/decode errors отсутствуют. При старте/seek ffplay насчитал 8, 8, 6 dropped frames соответственно; к отметке 65 s они уже были, далее до конца окна (~89 s) счётчик не менялся. Это не утверждение об отсутствии любых стартовых потерь или о побитовом совпадении кадров.

CPU policy0 в выборках 768–1804.8 MHz, policy6 825.6–1267.2 MHz. Полные выборки частот в results.json. Повторный аппаратный запуск воспроизвёл высокую нагрузку. Причина дополнительных затрат пока не установлена: необходимо отдельно профилировать ffplay/вывод NV12/ожидание V4L2, а не приписывать разницу самому Venus без доказательств.

После тестов полный фильм вновь запущен с начала через Venus, unit tcl-bbb-resume. Перезагрузок не было. Сценарий: ../playback-cpu.py; исходные результаты и stderr: results.json, hardware1.log, software.log, hardware2.log.

## Уточнение по визуальному качеству mpv

Пользователь сообщил о менее плавном движении и артефактах в начале полного аппаратного mpv. Поэтому аппаратный mpv не считать полностью исправным, даже при низком CPU и нулевых счётчиках drops в предыдущей сцене. В журнале начала полного фильма много VIDIOC_G_FMT ioctl. Связь этих запросов с повреждением картинки предполагается, не доказана.

Для контроля запущен полный фильм с --hwdec=no, остальные параметры видеовывода неизменны: gpu-next/OpenGL/Wayland, GL_RENDERER FD618. Журнал подтверждает Opening decoder h264, Using software decoding, yuv420p. Unit tcl-mpv-software; сейчас пользователь смотрит его. Без перезагрузок.

Дополнительный замер программного mpv (25.11s, ~65.53–90.64s после запуска процесса): mpv86.8%, Weston4.2% одного ядра; вся система12.5%. Аппаратный первый замер49.7/3.7/8.2% был с seek60+5s прогрев, поэтому окна близкие, но не покадрово идентичные. Это предварительная оценка, а не законченный A/B/A и не доказательство корректности аппаратного изображения. software-live.json намеренно помечен unmatched-scene. Повтор аппаратного замера и сравнение качества pending. Не смешивать проблемы Venus-декодирования и GPU-видеовывода.

2026-09-09: пользователь ответом «да» подтвердил, что контрольный mpv с программным H.264 (--hwdec=no) при прежнем GPU-выводе gpu-next/OpenGL/Wayland на FD618 показывает плавнее и без искажений. Аппаратный mpv ранее имел стартовые артефакты и менее плавное движение. Это сужает поиск к аппаратному пути Venus/V4L2/FFmpeg и его взаимодействию с mpv, но не доказывает дефект самого аппаратного блока либо конкретного компонента. Программный режим — подтверждённый визуальный контроль; аппаратный пока не считать полностью исправным. Просмотр не прерывался.

## Сравнение CPU при полном экранном воспроизведении, 2026-09-09

Пользователь подтвердил: Big Buck Bunny через Venus «выглядит прекрасно».

Сравнение ffplay: один файл официального Big Buck Bunny H.264 Main 1920x1080 24 fps; полный экран Weston GL, звук выключен. Каждый запуск с `-ss 60`, первые 5 s исключены, далее 25 s измерения. Порядок hardware → software → hardware. Программный декодер `-vcodec h264`, аппаратный `-vcodec h264_v4l2m2m`. Остальные параметры одинаковы; число потоков — автоматическое по умолчанию. Частоты/governor не фиксировались: это нагрузка в текущем обычном режиме системы, не сравнение при фиксированных частотах или измерение энергии.

CPU процесса получен из прироста utime+stime /proc/PID/stat: 100% означает одно полностью занятое ядро. Weston — сумма процессов с comm=weston. Общая загрузка из /proc/stat нормирована на все 8 CPU; idle и iowait исключены из busy.

| Режим | ffplay, % одного ядра | Weston, % одного ядра | Общая busy, % всех CPU |
|---|---:|---:|---:|
| hardware1 | 157.2 | 6.2 | 21.5 |
| software | 78.7 | 7.4 | 12.1 |
| hardware2 | 154.0 | 6.1 | 21.1 |

Вывод: в текущем ffplay аппаратный путь требует примерно вдвое больше процессорного времени плеера (154–157% против 78.7%). Общая загрузка всей машины 21.1–21.5% против 12.1%. Нельзя утверждать, что аппаратное воспроизведение уже экономит CPU/энергию. Ранее дешёвое декодирование ffmpeg → null относится к другому пути без экранного вывода и другому ролику.

Журналы обоих аппаратных запусков подтверждают qcom-venus /dev/video2. Corrupt/decode errors отсутствуют. При старте/seek ffplay насчитал 8, 8, 6 dropped frames соответственно; к отметке 65 s они уже были, далее до конца окна (~89 s) счётчик не менялся. Это не утверждение об отсутствии любых стартовых потерь или о побитовом совпадении кадров.

CPU policy0 в выборках 768–1804.8 MHz, policy6 825.6–1267.2 MHz. Полные выборки частот в results.json. Повторный аппаратный запуск воспроизвёл высокую нагрузку. Причина дополнительных затрат пока не установлена: необходимо отдельно профилировать ffplay/вывод NV12/ожидание V4L2, а не приписывать разницу самому Venus без доказательств.

После тестов полный фильм вновь запущен с начала через Venus, unit tcl-bbb-resume. Перезагрузок не было. Сценарий: ../playback-cpu.py; исходные результаты и stderr: results.json, hardware1.log, software.log, hardware2.log.
